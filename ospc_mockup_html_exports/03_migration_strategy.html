Migration Method Decision
7R Migration Methods
Each business system is first assigned a 7R migration method. The method defines whether the system should be retained, retired, rehosted, relocated, replatformed, refactored/containerized, or replaced. This prevents every workload from being treated as simple lift-and-shift and helps select the safest wave order.
R-Method Strategy Best used for Typical wave What happens Output
R1Retain Keep as-is Systems not ready, out of scope, or waiting for dependency changes Hold / later wave Leave workload on current platform and document reason Retain decision + revisit date
R2Retire Decommission Unused, duplicated, obsolete, or low-value systems Before Wave 1 Shut down safely after owner approval and backup/export Decommission record
R3Rehost Lift and shift VMs, simple apps, internal tools, low-risk systems Wave 1-2 Move VM/image/snapshot to FLEX with minimal change FLEX VM running
R4Relocate Move platform without app change Workloads that can move between compatible regions/clusters Wave 2-3 Move workload to another FLEX/OpenStack region or Kubernetes target Same workload in new location
R5Replatform Improve runtime Apps needing OS, DB, storage, LB, or config improvement Wave 2-4 Move to FLEX while improving platform services, DB, storage, or runtime Optimized FLEX workload
R6Refactor / Containerize Modernize app package Apps suitable for Kubernetes, GitOps, OpenCenter, or AI-ready modernization Wave 3+ Convert app into container image, manifests, Helm/Kustomize/Flux package OpenCenter-ready app package
R7Replace / Repurchase Replace with SaaS/new app Apps better replaced than migrated Any wave Move users/data to a new product or SaaS service Replacement plan + migration path
Default recommendation: R3 for low-risk lift-and-shift, R5 for platform optimization, R6 for containerized OpenCenter modernization.

Principle 6 — My Migration Plan: Wave-Based Execution

Migrate in ordered waves from lowest-risk to highest-risk. Each wave must fully pass UAT, health checks, and performance validation before the next wave begins. No wave starts until the previous one achieves ≥ 95% cutover confidence score.

W1

Wave 1 — Low-Risk Test Workloads

Isolated leaf systems with no downstream dependencies. Validates the FLEX migration pipeline end-to-end with zero customer impact.

First to Move

What Goes Here

  • Dev / staging / sandbox servers
  • CI/CD build agents
  • Test databases (non-production data)
  • Demo & POC instances
  • Monitoring probes

Migration Approach

  • R3 Rehost — lift & shift snapshot
  • Linux snapshot → FLEX volume
  • No replication needed
  • Scheduled off-hours window
  • Full pipeline dry-run validation
  • Smoke test only — no UAT gates

Success Criteria

  • Server boots on FLEX ✓
  • Network reachable ✓
  • Health endpoints return 200
  • Migration tool reports success
  • Runbook validated end-to-end
  • Team confidence > 90%
Risk Low
Downtime Acceptable
Rollback Simple restart
Duration Days 1–5
R3 Rehost
W2

Wave 2 — Internal Applications

Employee-facing tools and back-office systems. Low customer exposure, shallow dependency graphs. Downtime window during off-hours is acceptable.

Low Exposure

What Goes Here

  • HR portals & ticketing systems
  • Internal wikis & dashboards
  • VPN / jump hosts
  • Monitoring stacks (Grafana, etc.)
  • Log aggregators
  • Internal APIs

Migration Approach

  • R3 Rehost primary path
  • R5 Replatform for app + DB pairs
  • Pre-migrate & verify config
  • DNS flip within internal zones
  • Basic service comparison UAT
  • Off-hours cutover window

Success Criteria

  • All services running post-move ✓
  • Login / auth functional
  • Service comparison < 5% delta
  • Performance baseline met
  • Zero unresolved incidents
  • Cutover confidence ≥ 95%
Risk Low–Medium
Downtime Off-hours only
Rollback DNS revert
Duration Days 6–14
R3 Rehost R5 Replatform
W3

Wave 3 — Production Systems

Customer-facing application tier: web frontends, APIs, middleware, and stateless services. Full UAT and performance validation required before DNS cutover.

Full UAT Required

What Goes Here

  • Web frontends (nginx, Apache)
  • REST / GraphQL API servers
  • Application backends
  • Cache layers (Redis, Memcached)
  • Queue consumers (workers)
  • Load balancer configs

Migration Approach

  • R3 Rehost or R5 Replatform
  • R6 Containerize for cloud-native path
  • Parallel run on FLEX (shadow mode)
  • Full UAT business system tests
  • Performance delta < 15%
  • Staged DNS cutover (10% → 100%)

Success Criteria

  • UAT all tests PASS ✓
  • Response time ≤ OSPC baseline
  • Error rate < 0.1%
  • Health checks all green
  • Rollback plan tested & ready
  • Cutover confidence ≥ 97%
Risk Medium–High
Downtime Near-zero (staged)
Rollback DNS revert < 5 min
Duration Days 15–28
R3 Rehost R5 Replatform R6 Containerize
W4

Wave 4 — Databases & Critical Workloads

The persistence and data layer — the root of the dependency graph. Migrated via live replication with minimal cutover window. Everything depends on this wave succeeding.

Highest Risk

What Goes Here

  • MySQL / PostgreSQL / MariaDB
  • MongoDB / Cassandra clusters
  • RabbitMQ / Kafka brokers
  • Object / file storage backends
  • NFS / Ceph / Cinder volumes
  • Backup targets & archival stores

Migration Approach

  • R5 Replatform — live replication
  • Primary on OSPC → replica on FLEX
  • Replication lag monitored < 5 min
  • Read traffic shifted first
  • Write flip at planned cutover window
  • Freeze writes for < 60 seconds

Success Criteria

  • Replication lag = 0 at flip ✓
  • Zero data loss (RPO = 0)
  • All reads verified on FLEX
  • Write verification test passes
  • Rollback: re-sync back to OSPC
  • Cutover confidence = 99%
Risk High
Downtime < 60 sec write freeze
Rollback Replica re-sync
Duration Days 29–42
R5 Replatform
W5

Wave 5 — Final Cutover

Mission-critical core systems: identity, auth, billing, and compliance. All previous waves confirmed stable. This is the definitive OSPC decommission event.

Final Gate

What Goes Here

  • SSO / OAuth / LDAP / Keystone
  • Billing & payment systems
  • Compliance & audit logs
  • Certificate authorities
  • OSPC API endpoint (final DNS)
  • Legacy OSPC decommission

Migration Approach

  • R3 Rehost + DNS atomic flip
  • All teams on war room call
  • Cutover window ≤ 30 minutes
  • OSPC kept warm for 72 hrs
  • Final smoke test on every endpoint
  • OSPC decommission sign-off

Success Criteria

  • All users auth on FLEX ✓
  • Billing transactions verified ✓
  • Compliance audit trail intact
  • OSPC traffic = 0 for 24 hrs
  • Customer sign-off obtained ✓
  • Migration complete 🎉
Risk Managed
Downtime ≤ 30 min (planned)
Rollback DNS revert (72 hr warm)
Duration Days 43–50
R3 Rehost Final Cutover OSPC Decommission
