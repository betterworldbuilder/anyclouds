Stage 0 — Strategy & Business Case

Rackspace encourages OSPC (OpenStack Public Cloud) customers to upgrade to FLEX for its superior performance, cost savings, and modern capabilities.

🌟 Key Advantages

FLEX delivers enhanced scalability, high availability, and fault tolerance compared to legacy OSPC, enabling seamless handling of modern workloads like AI and Kubernetes. It avoids vendor lock-in through its open-source foundation, supports hybrid cloud strategies, and provides enterprise-grade security with 24/7 expert support. Customers can migrate workloads gradually without disruption, spinning up new projects on FLEX for better tooling and flexibility.

💰 Cost Benefits

Upgrading reduces total cost of ownership (TCO) with license-free operations and efficient resource scaling, outperforming proprietary platforms. FLEX offers cost management tools and no licensing fees, making it ideal for optimizing spend while maintaining reliability.

Switching from Legacy Rackspace Public Cloud (OSPC) to Rackspace OpenStack Flex typically offers lower licensing and long-term TCO but can involve similar or slightly higher per-VM compute costs, depending on sizing and region.

Below is a practical breakdown of costs and savings drivers and how they usually balance out.

Area How Flex reduces cost Typical saving angle
Licensing and vendor lock-in Flex is license-free, open-source OpenStack, unlike proprietary hyperscalers and some legacy-layer products. Lower TCO: no vendor-specific license fees, plus easier migration off-platform if needed.
Bandwidth and egress Flex advertises no egress-style overage fees (included bandwidth within its pricing model), unlike some hyperscalers that charge per-GB egress. High-traffic or hybrid apps gain: predictable monthly bills vs. "surprise" bandwidth spikes.
Infrastructure efficiency Newer, modern hardware and flexible scaling mean you can right-size VMs and avoid over-provisioning older OSPC-era instances. Moderate savings (roughly 10–30% TCO) if you optimize instance sizes and turn off unused VMs.

🚀 Future-Proofing

FLEX supports innovation with community-driven updates, custom networking, and multiple storage options for secure, performant environments. It's positioned as the successor to OSPC, bridging dedicated and multi-tenant clouds for long-term agility.

When to move to FLEX

Technical and business conditions triggering a migration from Legacy Rackspace Public Cloud (OSPC) to Rackspace OpenStack Flex (FLEX).

Condition / trigger Why it matters Example use case
Need for modern, OpenStack-based infrastructure FLEX runs on current-generation OpenStack with newer APIs, better automation, and alignment with upstream cloud standards, while OSPC is based on older, legacy Rackspace Cloud architecture. A company operating a legacy PHP app on OSPC wants to automate deployments with Terraform and Kubernetes; FLEX's OpenStack API and ecosystem support tools like Magnum and Terraform more natively.
Desire for more flexible networking and segmentation FLEX offers advanced networking (VLANs, segmentation within a single account, floating IPs, etc.), whereas OSPC has more rigid networking and lacks some modern segmentation capabilities. An e-commerce platform needs separate isolated networks for PCI-compliant payment workloads and analytics; FLEX allows segmented networks under one account, which OSPC cannot easily support.
Need to import custom images or use vendor images FLEX supports custom image uploads and lets you consume upstream images from vendors like Red Hat, Canonical, Microsoft, and SUSE; OSPC is more limited in this regard. A DevOps team wants to run a Red Hat Enterprise Linux image with a pre-built tuning profile; FLEX allows direct import or use of RH images, while OSPC would require extra workarounds.
Scaling beyond legacy limits or regions FLEX provides better scalability, multi-tenant capacity, and newer hardware; OSPC is being sunsetted and does not scale as easily into newer regions or hardware generations. A SaaS provider sees traffic doubling annually and wants to add bursting in a new region; FLEX lets them scale horizontally across regions with modern hardware, while OSPC will not be expanded.
Push toward cost-efficient, license-free infrastructure FLEX is a license-free, open-source-based private cloud, which can reduce some licensing and vendor-lock-in costs compared with older OSPC models. A financial services firm wants to cut licensing fees tied to proprietary cloud layers; they migrate app workloads from OSPC to FLEX to run on fully managed, open-source infrastructure.
Requirement for advanced automation and CI/CD pipelines FLEX integrates well with modern CI/CD and orchestration tools (e.g., Kubernetes, Terraform, Ansible) because it is built on current OpenStack, while OSPC tooling is more constrained. A startup wants GitOps-driven deployments using ArgoCD; FLEX's modern API and compute flavors make it easier to automate than OSPC's legacy surfaces.
Compliance or security posture upgrade FLEX adds newer security and compliance features and supports more granular segmentation and isolation, while OSPC is being deprecated and will not receive further security enhancements. A healthcare company must comply with updated data-residency and isolation rules; they migrate from OSPC to FLEX to leverage its improved security controls and segmentation.
Long-term roadmap: OSPC migration program Rackspace explicitly encourages and plans migration of OSPC workloads to the Flex platform, providing migration guidance and support. A customer still running legacy WebLogic servers on OSPC works with Rackspace to migrate those VMs to FLEX over a 6-month window, aligning with their expiry roadmap.

Stage 1 — Discovery & Assessment

Collect a full picture of the current OSPC environment before any migration work begins. The outputs of this stage feed directly into Stage 2.

📋 Tasks

  • Collect environment inventory – Gather details of all accounts, instances, images, volumes, and security groups.
  • Identify storage backend (Cinder) – Determine the storage technology in use to plan the appropriate migration approach.
  • Identify networking configuration & segmentation – ServiceNet, PublicNet, or Private Neutron Network.
  • Review quotas and utilisation – Evaluate current resource quotas and usage to properly size the Flex environment.
  • Identify unsupported features – Detect features/configurations not supported in Flex that require remediation before migration.

📦 Deliverables

  • Environment inventory – Detailed record of existing infrastructure (instances, storage, networking, security).
  • Capacity plan – Assessment of resource requirements to ensure Flex can support migrated workloads.
  • Migration risk assessment – Identification of potential risks, limitations, or unsupported features impacting migration.

📚 Simplest Discovery Path by Tooling

        
The best file to get from the existing OSPC deployment relies entirely on how the cluster was built. Do not blindly copy VM nodes or disks.


        

          

            
1) Helm-Managed App (Highest Priority)

            
Export the app configuration and rendered YAML. The values.yaml is the single most reusable import path for Flex.

            
helm list -A
helm get values <release> -n <namespace> -a -o yaml > <release>-values.yaml
helm get manifest <release> -n <namespace> > <release>-manifest.yaml

          


          

            
2) Kustomize-Managed App

            
Download the entire repository folder containing the kustomization.yaml, base manifests, patches, and overlays.

          


          

            
3) Raw Kubernetes YAML (Source Repo)

            
If a Git repo exists without Helm/Kustomize, download all declarative objects: deployment.yaml, statefulset.yaml, service.yaml, ingress.yaml, configmap.yaml, pvc.yaml.

          


          

            
4) Live Cluster Export (Fallback Path)

            
If there is ZERO source repository, fallback to exporting exactly what is running on OSPC. Note: this YAML will be messy and contain runtime state strings.

            
kubectl get all,cm,secret,ingress,pvc,networkpolicy -A -o yaml > k8s-inventory-main.yaml
kubectl get storageclass,pv -o yaml > k8s-storage-export.yaml

          


          

            
Infrastructure Mapping Database

            
You MUST execute these to map Kubernetes to OpenStack Nova VMs and Cinder Storage.

            
kubectl get nodes -o wide
openstack server list --all-projects --long   # Map Internal K8s IPs to OSPC VM IDs
kubectl get pvc -A -o wide
openstack volume list --long   # Map Bound PVs to OpenStack Cinder Volume IDs

Stage 7

        
IaC Backup, DR & Restore

        
Terraform + Ansible recovery pack

        
Capture the migrated tenant state as reusable Terraform and Ansible artifacts. Use this stage to export the recovery pack, validate restore readiness, and rebuild the tenant in the same region, another region, or another OpenStack-compatible cloud.

        
For GitOps/OpenCenter-based redeployments, publish the same recovery pack to the GitOps repository and continue in Stage 8 — GitOps & OpenCenter Modernization.

      


      

        
How this stage works

        

          
1. Backup source

          The IaC recovery pack is created from the Migration Output Bundle generated in Stage 5 — Stabilization & Handover. When you click Generate Bundle in Stage 5, the system writes a timestamped bundle directory for the active customer. The bundle includes tenant-iac-dr/, which contains Terraform environment stubs, Ansible inventory snippets, backup-policy.yaml, restore runbooks, metadata, and restore scope documentation. This is an infrastructure-definition backup. It does not include full VM disk images, application binaries, or database row dumps. Full scope details are recorded in tenant-iac-dr/dr/BACKUP_SCOPE.md.

          
2. Backup export and publishing

          After Stage 5 succeeds, the dashboard keeps the latest bundle stamp for the session. Use Export IaC Backup to copy tenant-iac-dr/ into a configured Git working tree and/or upload backup archives to object storage.

          
Supported environment variables:

          
    
            
  • IAC_BACKUP_GIT_REPO_PATH
    • 
            
  • GITOPS_REPO_PATH
    • 
            
  • IAC_BACKUP_S3_BUCKET
    • 
            
  • GITOPS_PUSH_AFTER_COMMIT
    • 
          

          
3. Restore execution

          Restore consumes the same tenant-iac-dr/ recovery pack. Save the Target Cloud Profile, confirm the readiness banner shows that the Stage 5 bundle includes tenant-iac-dr/, then choose one restore path:

          
Option A — Direct Terraform / OpenStack Restore — same-region, cross-region, or cross-cloud OpenStack rebuilds without OpenCenter lifecycle automation.
