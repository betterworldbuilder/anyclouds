Stage 1 – Discovery & Assessment

Collect a full picture of the current OSPC environment before any migration work begins. The outputs of this stage feed directly into Stage 2.

📋 Tasks

  • Collect environment inventory – Gather details of all accounts, instances, images, volumes, and security groups.
  • Identify storage backend (Cinder) – Determine the storage technology in use to plan the appropriate migration approach.
  • Identify networking configuration & segmentation – ServiceNet, PublicNet, or Private Neutron Network.
  • Review quotas and utilisation – Evaluate current resource quotas and usage to properly size the Flex environment.
  • Identify unsupported features – Detect features/configurations not supported in Flex that require remediation before migration.

📦 Deliverables

  • Environment inventory – Detailed record of existing infrastructure (instances, storage, networking, security).
  • Capacity plan – Assessment of resource requirements to ensure Flex can support migrated workloads.
  • Migration risk assessment – Identification of potential risks, limitations, or unsupported features impacting migration.

📚 Simplest Discovery Path by Tooling

The best file to get from the existing OSPC deployment relies entirely on how the cluster was built. Do not blindly copy VM nodes or disks.

1) Helm-Managed App (Highest Priority)

Export the app configuration and rendered YAML. The values.yaml is the single most reusable import path for Flex.

helm list -A
helm get values <release> -n <namespace> -a -o yaml > <release>-values.yaml
helm get manifest <release> -n <namespace> > <release>-manifest.yaml

2) Kustomize-Managed App

Download the entire repository folder containing the kustomization.yaml, base manifests, patches, and overlays.

3) Raw Kubernetes YAML (Source Repo)

If a Git repo exists without Helm/Kustomize, download all declarative objects: deployment.yaml, statefulset.yaml, service.yaml, ingress.yaml, configmap.yaml, pvc.yaml.

4) Live Cluster Export (Fallback Path)

If there is ZERO source repository, fallback to exporting exactly what is running on OSPC. Note: this YAML will be messy and contain runtime state strings.

kubectl get all,cm,secret,ingress,pvc,networkpolicy -A -o yaml > k8s-inventory-main.yaml
kubectl get storageclass,pv -o yaml > k8s-storage-export.yaml

Infrastructure Mapping Database

You MUST execute these to map Kubernetes to OpenStack Nova VMs and Cinder Storage.

kubectl get nodes -o wide
openstack server list --all-projects --long   # Map Internal K8s IPs to OSPC VM IDs
kubectl get pvc -A -o wide
openstack volume list --long   # Map Bound PVs to OpenStack Cinder Volume IDs

🔬 Internal UAT Tasks Reference

🔬 Internal UAT Tasks

  • Verify VM boot – Ensure VMs start successfully in Flex. 
    openstack server list --project <project_id> -c Name -c Status | grep ACTIVE
  • Validate network connectivity – Confirm instances communicate as expected. 
    ping -c 4 <flex_floating_ip>
    nc -zv <flex_private_ip> 22
  • Confirm storage accessibility – Verify volumes and storage resources are accessible. 
    openstack volume list --project <project_id> -c Name -c Status
    ssh user@<flex_ip> 'df -h | grep /dev/vd'

👤 Customer UAT Tasks

  • Access confirmed – Customer confirmed access to the new Flex environment.
  • Confirm application functionality – Applications operating correctly after migration.

🛠 Automated Checking Commands

Databases (Service & Replication)

# MySQL Replication Status
ssh admin@<db_ip> 'mysql -e "SHOW SLAVE STATUS\\G" | grep "Running:"'

# PostgreSQL Replication
ssh postgres@<db_ip> 'psql -xc "select * from pg_stat_replication;"'

App Tiers (DNS & Services)

# Check DNS Resolution
dig @<flex_dns> +short <app_url>

# Verify Web Service HTTP 200
curl -I -s https://<app_url> | head -n 1

# Systemd Service Status
ssh user@<app_ip> 'systemctl is-active <service_name>'

Containers (Pod/PVC Health)

# Verify Kubernetes Workload Health
kubectl get pods,pvc,ingress -n <namespace>

Stage 5 – Cutover

Redirect production traffic from OSPC to Flex. Typically done during a scheduled maintenance window to minimise impact.

⚡ Tasks

  • Update DNS or floating IPs – Redirect traffic by updating DNS records or reassigning floating IPs.
  • Confirm production traffic flow – Verify live traffic is reaching the new environment.
  • Monitor workloads – Observe system performance and stability after cutover.

📦 Deliverable

  • Customer confirms the application is running successfully in the Flex environment.
⚠️ Ensure rollback scripts (generated in Stage 3) are ready before initiating cutover.
