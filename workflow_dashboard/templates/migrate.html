    Step 6) Generate Data Migration Artifacts Idle

    This step is the planning and scripting engine. When you select your inputs (either the OpenStack mappings from Stage 1 or a custom CSV) and choose a Migration Strategy, the backend python script (generate_data_migration_script.py) analyzes the source servers and target clones to build a customized migration runbook.

    It generates three distinct, reusable Bash scripts:

    • *_sync.sh (The Background Copy): Securely copies files (rsync) or copies databases (mysqldump) from the live OSPC source to the FLEX target while the application is still running. This step is 100% non-disruptive and can be run multiple times to keep the target "warmed up."
    • *_cutover.sh (The Final Switch): The critical script that executes the strategy you chose (Direct, Local A/B, or External A/B). It stops the source services to freeze data writes, performs one final lightning-fast delta sync to the target, and updates local proxies or OpenStack Load Balancers to permanently route live user traffic to the new FLEX instance.
    • *_rollback.sh (The Safety Net): Automatically generated safety script that immediately reverses the cutover commands (e.g. removes the FLEX instance from the load balancer and restarts the legacy OSPC services) if the migration fails validation.

    Step 7) Execute Data Migration Idle

    This step is the execution engine. Instead of forcing you to SSH into jump boxes to run the scripts manually, the dashboard acts as a secure control plane.

    • You use the dropdown to select one of the three scripts generated in Step 6 (usually starting with the _sync.sh script).
    • When you click Execute Migration Script, the dashboard's backend securely spawns a bash sub-process.
    • The script executes the remote payload delivery (e.g., streaming rsync over SSH between the source and target IPs).
    • All standard output and errors are captured live and streamed directly into the Execution Output window at the bottom of the dashboard, giving you complete visibility into the progress of the packet transfers and database dumps.

    Step 8.5) Kubernetes (K8s) Migration Manual & Automated

    Because Kubernetes manages its own state and storage dependencies, we do not migrate them using standard VM-level rsync scripts. Choose the Automated Pipeline or one of the manual fallback strategies below:

    How it works

    1. You select the Deployment Type dropdown (Helm, Kustomize, or Raw YAML).
    2. You upload your Stage 1 Export Configuration (e.g. k8s-inventory-main.yaml or ZIP).
    3. You provide the path to your target FLEX Kubeconfig file.
    4. You click the big purple Execute Kubernetes Redeployment button.

    The Python backend engine (app.py) will automatically take those exact parameters, inject the Kubeconfig context into an isolated environment, and execute the correct deployment binary for you:

    • For Helm, it runs: helm upgrade --install <release> . -f <values-path>
    • For Kustomize, it runs: kubectl apply -k <kustomize-path>
    • For Raw YAML, it runs: kubectl apply -f <yaml-path>

    The execution logs are then streamed straight back into the dashboard! This makes rebuilding the K8s configurations a true 1-click operation without your operators ever having to touch a terminal.

    ⚡ Automated Pipeline: Stage 1 Artifact Deployment

    Automatically deploy the Kubernetes configurations (YAML/Helm/Kustomize) exported during Stage 1 directly onto the new FLEX cluster.

    1. Ensure the newly provisioned FLEX Kubernetes Cluster is online.
    2. Ensure any Cinder storage volumes have been successfully snapshot and re-attached in FLEX.
    3. Select the deployment type (Helm, Kustomize, or Raw YAML) and provide the file paths below.

    Manual Strategy A: Cinder Volume Snapshot & Configuration Rebuild

    Best for clusters with giant Persistent Volumes (Databases, Message Queues) when you don't want to use Velero.

    1. Back in Stage 1 (Discovery), export all configurations based on the source tooling (e.g. Helm values, Kustomize folder, or cleaned raw YAML).
    2. Scale down the StatefulSets in OSPC to freeze data pipelines: kubectl scale statefulset <name> --replicas=0.
    3. Snapshot the underlying Cinder Volumes in the OSPC OpenStack project.
    4. Create new Cinder Volumes from those snapshots in the FLEX project, ensuring they match capacity.
    5. Deploy the new FLEX Kubernetes Cluster.
    6. Update your PersistentVolume manifests in FLEX to bind directly to the newly cloned FLEX Volume IDs.
    7. During Stage 3, switch your terminal context to the new FLEX cluster's API and apply your exported configurations:
      • Helm: helm upgrade --install <release> <chart> -n <namespace> -f values.yaml
      • Kustomize: kubectl apply -k <directory>
      • Raw YAML / Live Export: kubectl apply -f k8s-inventory-main.yaml (ensure you removed old runtime uids/ips).
    8. Update Ingress Route53/DNS.

    Manual Strategy B: Backup & Restore via Velero (Cloud-Native Sync)

    The recommended Kubernetes-native manual approach that perfectly preserves all Custom Resources, Secrets, and Namespaces.

    1. Provision an empty target Kubernetes cluster running on your FLEX OpenStack VMs.
    2. Install Velero on the legacy OSPC Cluster, configured to backup workloads to an S3/Swift Object Storage bucket.
    3. Run a full cluster backup: velero backup create k8s-migration --include-namespaces <your-apps>.
    4. Install Velero on the new FLEX Cluster, pointing to the exact same shared bucket.
    5. Run the restore command onto FLEX: velero restore create --from-backup k8s-migration.
    6. Validate the restored pods, test workload communication over the new FLEX overlay network, and cutover DNS.
