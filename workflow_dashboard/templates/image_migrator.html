How this tool works

This VM migration tool allows us to move live OSPC VMs or static OSPC VM images entirely from OpenStack to Flex. The pipeline ensures all original VM content, users, and disks are carried over intact across the datacenter.

Architectural Advantage: By centralizing execution onto a dedicated Deployment Jumphost, we guarantee unparalleled robustness, safety, and performance. Both pipelines completely bypass unpredictable origin VM network configurations, origin disk space exhaustion anomalies, and legacy OS tooling failures.

💡 Engineering Recommendation: When to use which?

🚀 Use Hot Server Migration when:
  • Migrating at scale: You have dozens of VMs and want full end-to-end automation without manually powering down and imaging each one first.
  • Uptime is critical: The origin workload must stay online serving traffic while the orchestration engine works in the background.
  • You want "One-Click": Select 50 VMs, hit Start, and walk away.
🖼 Use Cold Image Migration when:
  • Migrating DBs / Fragile states: API snapshots on active transactional databases can cause data inconsistencies. Safely imaging them offline first ensures flawless ports.
  • Speed is paramount: The VM originates from massive volumes and you want to skip the LIVE snapshot generation stage entirely to save hours.
  • Porting Golden Templates: Pushing pre-baked blank server templates currently statically idling in the old registry.

🖼 OSPC Snapshot Discovery & Cold Migration
Cold Migration (Fastest)
⚡ Recommended: Use a Jumphost deployed in the same region as the origin OSPC VMs or snapshots for fastest transfer speeds and lowest latency.
  1. Scan Private Snapshots: Discovers all private tenant snapshot images in the selected OSPC region via Glance API.
  2. Download Image: Jumphost streams the raw image bit-stream from OSPC Glance using regional auth tokens.
  3. Convert to QCOW2: Converts the downloaded image to FLEX-compatible qcow2 format using qemu-img convert.
  4. Offline Disk Repair: Auto-detects OS type and applies chroot-based fixes (fstab, initramfs, network config, virtio drivers) without booting the VM.
  5. Upload to FLEX Glance: Pushes the repaired image into FLEX Glance with auto-injected os_type and hw_qemu_guest_agent=yes metadata.
  • Extremely fast (no live snapshot wait).
  • Fully offline repair — no VM boot required.
  • Preserves golden baseline integrity.
  • Same-region jumphost minimizes transfer time.
The absolute fastest and safest cold migration method. Perfect for porting golden server templates, exact point-in-time static backups, or bulk snapshot migrations.

🚀 OSPC Server Batch NBD
Hot Migration (Live Servers)
  1. Snapshot: Queries OSPC API to live-snapshot the Origin VM.
  2. High-Speed Export: Jumphost pulls snapshot from Glance at Datacenter backbone speeds.
  3. Local Transcode: Jumphost transcodes block device to KVM-optimized .qcow2.
  4. Inline Repair: Native NBD mounting applies OS-specific fixes (VirtIO, fstab, grub) directly offline.
  5. FLEX Boot: Repaired disk is streamed to FLEX API and booted using mapped network specs.
  • Decouples from origin network layout.
  • Automated OS hypervisor injection.
  • Zero manual SSH required on source.
A true hot migration method. Automatically takes an API snapshot and moves live servers when needed without shutting down the origin instances. Ideal for active workloads.

▶ Detailed Windows Offline Repair Steps
Step Action Name What the Script Does
1VirtIO ISO StagingDownloads virtio-win.iso from Fedora (with fallback) and loop-mounts it to access the KVM drivers.
2Mount Windows ImageExposes qcow2 via qemu-nbd, cleans filesystem with ntfsfix, detects BitLocker, and natively mounts C:\ part.
3Detect Windows VersionParses offline SOFTWARE hive using hivexsh to map the exact Windows version to the correct ISO driver folder.
4Copy VirtIO DriversCopies viostor, netkvm, balloon, and vioserial directly into System32\drivers and the Windows DriverStore.
5Inject Registry ServicesRewrites the SYSTEM registry hive using hivexregedit to map new VirtIO drivers as Critical Boot-Start (Start=0).
6Registry VerificationQueries the registry back out via hivexsh to guarantee the VirtIO disk drivers were effectively configured to auto-start.
7Disable OSPC Zen PV driversSuppresses legacy Zen hypervisor PV services (xenvbd, xennet) in the registry (Start=4) to prevent Boot BSOD.
8Enable Storage StackScans Microsoft's generic disk controllers (disk, volmgr, partmgr) to ensure they initialize alongside KVM.
9Cleanup & SentinelsGracefully unmounts the C:\ filesystem, detaches qemu-nbd, and writes a .win_repaired cache sentinel file.

Label lock is OFF — workflow-scoped cleanup (active for your next jumphost runs)
The dashboard sends disable_method_d_lock=1 and pre-launch pkill is limited by workflow tag (e.g. Method G vs Method H capture), not a single broad match on every method_d_capture for the label.
  • Coexistence: Method G and Method H must not kill each other by mistake (the old broad pkill); jobs that should coexist without cross-kill rely on this workflow-tagged cleanup on the jumphost.
  • Still not magic: if two jobs truly run at the same time against the same VM / same label, you can still get double full-disk capture, heavy guest IO, and overlapping artifacts — the lock is what prevents that class of overlap.
Create new boot repair script / Force new — Applies to Method C (CloudJumper) only: clears the "resume" path so compare + repair bundle generation runs from scratch instead of reusing the last saved CloudJumper artifacts.

Target Windows preparation for comparison (Method C)
Use when target FLEX Windows VM is reachable by RDP but CloudJumper cannot reach SSH/WinRM.
1) RDP into target (copy/paste)
xfreerdp /v:<TARGET_PUBLIC_IP> /u:Administrator /p:'<TARGET_PASSWORD>' /cert:ignore /sec:nla
Replace placeholders with your target FLEX VM public IP and password.
2) Enable WinRM (5985) + attempt OpenSSH (22)
Open PowerShell as Administrator on the target VM and paste this exact block (single paste, no manual line breaks):
$ErrorActionPreference = 'Continue'

# WinRM
Set-Service WinRM -StartupType Automatic -ErrorAction SilentlyContinue
Start-Service WinRM -ErrorAction SilentlyContinue
winrm quickconfig -quiet
winrm set winrm/config/service '@{AllowUnencrypted="true"}' | Out-Null
winrm set winrm/config/service/auth '@{Basic="true"}' | Out-Null
if (-not (Get-NetFirewallRule -DisplayName "ospc2flex-WinRM" -ErrorAction SilentlyContinue)) {
    New-NetFirewallRule -DisplayName "ospc2flex-WinRM" -Direction Inbound -Protocol TCP -LocalPort 5985 -Action Allow -Profile Any | Out-Null
}

# OpenSSH (Windows Server 2016 safe)
$capName = "OpenSSH.Server~~~~0.0.1.0"
$cap = Get-WindowsCapability -Online -Name $capName -ErrorAction SilentlyContinue
if ($cap -and $cap.State -ne 'Installed') {
    Add-WindowsCapability -Online -Name $capName | Out-Null
}

# If capability method unavailable, try built-in service path
if (Get-Service sshd -ErrorAction SilentlyContinue) {
    Set-Service sshd -StartupType Automatic -ErrorAction SilentlyContinue
    Start-Service sshd -ErrorAction SilentlyContinue
}

if (-not (Get-NetFirewallRule -DisplayName "ospc2flex-SSH" -ErrorAction SilentlyContinue)) {
    New-NetFirewallRule -DisplayName "ospc2flex-SSH" -Direction Inbound -Protocol TCP -LocalPort 22 -Action Allow -Profile Any | Out-Null
}

Write-Host "[ospc2flex] WinRM(5985) configured; SSH(22) attempted."
After this, rerun Method C. CloudJumper should be able to collect the target profile via WinRM and generate the dynamic bundle.
