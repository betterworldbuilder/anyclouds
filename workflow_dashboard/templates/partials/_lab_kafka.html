🚊 Building the Digital City's Postal and Railway System

The city is built. Now its applications need a dependable way to exchange information.
Your OpenCenter city already has FLEX infrastructure, Kubernetes, GitOps, networking, storage, monitoring and security. In this lab you build Kafka — the postal service and railway network. Applications place events onto named routes; Kafka stores them, carries them, and lets many services receive them without being directly connected.
Read this first Service names, image tags and supported fields differ between OpenCenter and Strimzi releases. Every task below tells you to confirm the real name from opencenter cluster describe or kubectl explain before you type it. Never enable an invented service name.

OpenCenter ships kafka-cluster as an optional workload service, disabled by default because not every cluster needs an event-streaming platform. The GitOps base provides Strimzi as the Kubernetes operator that deploys and manages the Kafka resources.

The simple metaphor

Kafka organises events into topics. Producers write; consumers read and process independently. That separation is what lets applications communicate without depending on each other.

Lab variables

Create a local environment file. Every command below uses these variables, so you only change values in one place.

cat > kafka-lab.env <<'EOF'
export LAB_ORG="my-company"
export LAB_CLUSTER="prod-cluster"

export KAFKA_NAMESPACE="kafka-lab"
export KAFKA_CLUSTER="city-stream"
export KAFKA_TOPIC="city-events"

# Current official Strimzi example image.
# Change this when your installed operator supports a different version.
export KAFKA_CLIENT_IMAGE="quay.io/strimzi/kafka:1.1.0-kafka-4.3.0"
EOF
Load it and select the cluster
source kafka-lab.env

opencenter cluster use "$LAB_ORG/$LAB_CLUSTER"

# Load its Kubernetes access into this shell
eval "$(opencenter cluster use "$LAB_ORG/$LAB_CLUSTER" --export-only)"
Find and confirm the GitOps working directory
export GITOPS_DIR="$(
  opencenter cluster describe "$LAB_ORG/$LAB_CLUSTER" 2>/dev/null |
  awk '/git_dir:/ {print $2; exit}'
)"

printf 'GitOps directory: %s\n' "$GITOPS_DIR"
test -d "$GITOPS_DIR"
Stop if this fails If test -d returns non-zero, GITOPS_DIR did not resolve. Every GitOps task in this lab writes into that directory — fix it now rather than committing into the wrong tree.

Part 2 · Build and use the railway Missions 3–5🚆 Cluster, topics, traffic
3Build the Kafka Cluster 40 minkubectlstrimzi Three sorting offices, each with its own warehouse.
The metaphor The operations department exists; now it builds the sorting offices. Three nodes, each with a persistent Cinder warehouse, so a parcel is never held by only one office.
Task 3.1 — Create the namespace
kubectl create namespace "$KAFKA_NAMESPACE" --dry-run=client -o yaml | kubectl apply -f -
kubectl get ns "$KAFKA_NAMESPACE"
Task 3.2 — Confirm the version your operator supports
# Never guess the Kafka version - ask the installed CRD
kubectl explain kafka.spec.kafka.version
kubectl get crd kafkas.kafka.strimzi.io -o jsonpath='{.spec.versions[*].name}'; echo
Task 3.3 — Declare the node pool and the cluster

Modern Strimzi runs Kafka in KRaft mode — no ZooKeeper — and nodes are declared through a KafkaNodePool. Write this into your GitOps tree, not straight to the cluster.

cat > "$GITOPS_DIR/kafka-city-stream.yaml" <<EOF
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaNodePool
metadata:
  name: city-pool
  namespace: ${KAFKA_NAMESPACE}
  labels:
    strimzi.io/cluster: ${KAFKA_CLUSTER}
spec:
  replicas: 3
  roles:
    - controller
    - broker
  storage:
    type: jbod
    volumes:
      - id: 0
        type: persistent-claim
        size: 100Gi
        deleteClaim: false
---
apiVersion: kafka.strimzi.io/v1beta2
kind: Kafka
metadata:
  name: ${KAFKA_CLUSTER}
  namespace: ${KAFKA_NAMESPACE}
spec:
  kafka:
    listeners:
      - name: plain
        port: 9092
        type: internal
        tls: false
      - name: tls
        port: 9093
        type: internal
        tls: true
    config:
      offsets.topic.replication.factor: 3
      transaction.state.log.replication.factor: 3
      transaction.state.log.min.isr: 2
      default.replication.factor: 3
      min.insync.replicas: 2
  entityOperator:
    topicOperator: {}
    userOperator: {}
EOF
Two version-dependent details
  • Operators older than Strimzi 1.0 also need the annotations strimzi.io/node-pools: enabled and strimzi.io/kraft: enabled on the Kafka resource. Newer ones reject or ignore them.
  • If kubectl explain in Task 3.2 showed spec.kafka.version as required, add it with a value your operator supports.
  • Omitting storage.class uses the cluster default from Task 1.4. Set it explicitly if you need a specific Cinder type.

4Topics, Producers and Consumers 40 minkubectlkafka-cli Open a delivery route, then send and receive your first parcels.
The metaphor A topic is a named delivery route. Six partitions are six lanes on that route — the reason more than one delivery van can work it at the same time.
Task 4.1 — Declare the topic
cat > "$GITOPS_DIR/kafka-topic-city-events.yaml" <<EOF
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaTopic
metadata:
  name: ${KAFKA_TOPIC}
  namespace: ${KAFKA_NAMESPACE}
  labels:
    strimzi.io/cluster: ${KAFKA_CLUSTER}
spec:
  partitions: 6
  replicas: 3
  config:
    retention.ms: 604800000
    segment.bytes: 1073741824
EOF

git -C "$GITOPS_DIR" add kafka-topic-city-events.yaml
git -C "$GITOPS_DIR" commit -m "Add ${KAFKA_TOPIC} topic"
git -C "$GITOPS_DIR" push
flux reconcile source git flux-system

retention.ms: 604800000 is seven days — how long the warehouse keeps a parcel after delivery. This is the setting that makes replay possible.

Task 4.2 — Confirm the Topic Operator created it
kubectl -n "$KAFKA_NAMESPACE" get kafkatopic
kubectl -n "$KAFKA_NAMESPACE" describe kafkatopic "$KAFKA_TOPIC"
Task 4.3 — Send city events (producer)

Open a terminal. Type a line, press Enter — that is one event.

kubectl -n "$KAFKA_NAMESPACE" run kafka-producer -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-console-producer.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --topic "$KAFKA_TOPIC"

# Then type, one per line:
#   vm.migrated  server-01  DFW->IAD3
#   cutover.started  acme-payments
#   uat.approved  acme-payments
Task 4.4 — Receive them (consumer)

In a second terminal (remember to source kafka-lab.env there too):

kubectl -n "$KAFKA_NAMESPACE" run kafka-consumer -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-console-consumer.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --topic "$KAFKA_TOPIC" \
    --from-beginning
The point of the exercise --from-beginning replays events that were sent before this consumer existed. A queue could not do that — the message would have been consumed and deleted. This is the single most important difference between Kafka and RabbitMQ, and you have just demonstrated it.
Mission complete when
  • The KafkaTopic shows Ready with 6 partitions.
  • Events typed in the producer appear in the consumer.
  • A second consumer started later still sees the earlier events with --from-beginning.
5Consumer Groups and Partitions 30 minkafka-cli A delivery team sharing the lanes, instead of one van doing everything.
The metaphor A consumer group is a delivery team. Kafka assigns lanes (partitions) across the team. Add a van, each van carries fewer lanes. Lose a van, its lanes are reassigned automatically.
Task 5.1 — Start two consumers in the same group

Run this in two terminals, changing only the pod name:

kubectl -n "$KAFKA_NAMESPACE" run kafka-team-1 -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-console-consumer.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --topic "$KAFKA_TOPIC" \
    --group city-team

# second terminal: same command, pod name kafka-team-2
Task 5.2 — Produce a burst and watch the split
kubectl -n "$KAFKA_NAMESPACE" run kafka-burst -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bash -c 'for i in $(seq 1 60); do echo "city-event-$i"; done | \
    bin/kafka-console-producer.sh \
      --bootstrap-server '"$KAFKA_CLUSTER"'-kafka-bootstrap:9092 \
      --topic '"$KAFKA_TOPIC"''

Expected: the 60 events are split between the two consumers — not duplicated to both. That is a group sharing work. Two consumers in different groups would each get all 60.

Task 5.3 — Inspect the group and its lag
kubectl -n "$KAFKA_NAMESPACE" run kafka-admin -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-consumer-groups.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --describe --group city-team

Read the PARTITION, CURRENT-OFFSET, LOG-END-OFFSET and LAG columns. Lag is the single number that tells you a consumer is falling behind — it is what you will alert on in production.

Task 5.4 — Kill one consumer, watch rebalancing
# Ctrl-C one of the two consumers, then immediately:
kubectl -n "$KAFKA_NAMESPACE" run kafka-admin -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-consumer-groups.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --describe --group city-team

Expected: all six partitions are now assigned to the surviving consumer. No events were lost.

Mission complete when
  • Two consumers in one group split the partitions rather than duplicating events.
  • You can read lag per partition and say what it means.
  • Removing a consumer rebalances its partitions onto the survivor with no loss.
Part 3 · Prove it survives Missions 6–8🔥 Failure, sight, locks
6Persistence and Failure Recovery 35 minkubectlstrimzi Burn down a sorting office and prove the parcels survive.
The metaphor A sorting office closes unexpectedly. Because every parcel was copied to other offices and the warehouse is separate from the building, nothing is lost and deliveries continue.
Task 6.1 — Record the state before the failure
kubectl -n "$KAFKA_NAMESPACE" get pods -o wide
kubectl -n "$KAFKA_NAMESPACE" get pvc

# Note the end offsets - this is your "before" evidence
kubectl -n "$KAFKA_NAMESPACE" run kafka-admin -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-get-offsets.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --topic "$KAFKA_TOPIC"
Task 6.2 — Cause a controlled failure
# Delete ONE broker pod. Never scale the node pool to 0 to simulate this.
kubectl -n "$KAFKA_NAMESPACE" delete pod "$KAFKA_CLUSTER-city-pool-0"

kubectl -n "$KAFKA_NAMESPACE" get pods -w
Do not delete the PVC Deleting the pod tests recovery. Deleting the PersistentVolumeClaim destroys the warehouse and is data loss, not a drill. deleteClaim: false in Mission 3 is what protects you here.
Task 6.3 — Prove the data survived
kubectl -n "$KAFKA_NAMESPACE" wait kafka/"$KAFKA_CLUSTER" \
  --for=condition=Ready --timeout=600s

# Same offsets as before? Then nothing was lost.
kubectl -n "$KAFKA_NAMESPACE" run kafka-admin -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-get-offsets.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --topic "$KAFKA_TOPIC"

# And replay everything from the start
kubectl -n "$KAFKA_NAMESPACE" run kafka-verify -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-console-consumer.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --topic "$KAFKA_TOPIC" \
    --from-beginning --timeout-ms 15000
Task 6.4 — Check under-replicated partitions
kubectl -n "$KAFKA_NAMESPACE" run kafka-admin -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-topics.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --describe --under-replicated-partitions

Expected: empty output once the replacement broker has caught up. Any lasting output here means a replica has not re-synced.

Mission complete when
  • The deleted broker was rebuilt automatically by Strimzi.
  • It re-attached its existing PVC rather than provisioning a new one.
  • Offsets match the pre-failure reading and all events replay.
  • No under-replicated partitions remain.
  • You recorded how long recovery took — that is your measured RTO.

8Security Challenge 35 minstrimzikubectl Not everyone may post a parcel, and not on every route.
The metaphor Until now, anyone inside the city could post anything on any route. A real postal system checks who you are, and what you are allowed to send.
Task 8.1 — Add an authenticated listener and authorization

Add a listener to spec.kafka.listeners, and authorization at the same level as listeners:

      - name: scram
        port: 9095
        type: internal
        tls: true
        authentication:
          type: scram-sha-512

    authorization:
      type: simple
Order matters Turning on authorization denies everything not explicitly allowed. Apply this before you create the user in 8.2, then verify the existing plain listener on 9092 still works for the earlier missions — or accept that they now need credentials too.
Task 8.2 — Create a user with least privilege
cat > "$GITOPS_DIR/kafka-user-city-writer.yaml" <<EOF
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaUser
metadata:
  name: city-writer
  namespace: ${KAFKA_NAMESPACE}
  labels:
    strimzi.io/cluster: ${KAFKA_CLUSTER}
spec:
  authentication:
    type: scram-sha-512
  authorization:
    type: simple
    acls:
      - resource:
          type: topic
          name: ${KAFKA_TOPIC}
          patternType: literal
        operations:
          - Describe
          - Write
EOF

git -C "$GITOPS_DIR" add kafka-user-city-writer.yaml
git -C "$GITOPS_DIR" commit -m "Add least-privilege city-writer user"
git -C "$GITOPS_DIR" push
flux reconcile source git flux-system
Task 8.3 — Collect the generated credential
kubectl -n "$KAFKA_NAMESPACE" get kafkauser city-writer

# The User Operator generates the password into a Secret named after the user
kubectl -n "$KAFKA_NAMESPACE" get secret city-writer \
  -o jsonpath='{.data.password}' | base64 -d; echo
Lab only Printing a password to a terminal is acceptable in an isolated training sandbox and nowhere else. In production this Secret is consumed by the workload directly, and the GitOps copy is encrypted with SOPS — see Module 7 of the Advanced lab.
Task 8.4 — The challenge
Prove all four, with evidence
  • city-writer can write to city-events.
  • city-writer cannot read from city-events — the ACL grants only Describe and Write.
  • city-writer cannot write to any other topic.
  • An unauthenticated client is refused on the scram listener.
Capture the exact error message for each denial. "It failed" is not evidence; TopicAuthorizationException is.
Mission complete when
  • An authenticated listener and simple authorization are live.
  • city-writer exists with only the ACLs it needs.
  • All four outcomes in 8.4 are demonstrated with their error messages recorded.
  • Every change went through Git, not kubectl edit.

  • Why is Kafka an operator-managed service rather than an ordinary Deployment?
  • What did --from-beginning demonstrate that a queue cannot do?
  • What is consumer lag, and at what value would you page someone?
  • What exactly survived the broker deletion in Mission 6, and why?
  • Which single metric would you put on the control-room wall, and why that one?
  • Name one workload in your own estate that should not get Kafka, and say why.
Lab complete when
  • Evidence file captured before teardown.
  • Every resource was removed through Git, not by hand.
  • The OpenCenter service is disabled and the blueprint validates clean.
  • No orphaned PVCs or Cinder volumes remain.
  • All six graduation questions answered with evidence.
Related Kafka is deliberately kept out of the Advanced OpenCenter Training Lab — it is a workload-specific capability, not something every cluster needs, and it is large enough to deserve its own programme. The Advanced lab covers the platform this one is built on: worker pools and capacity (Module 8), secrets management (Module 7), observability (Module 9) and GitOps discipline throughout.
