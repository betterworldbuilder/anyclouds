📚 Migration Prioritization Guidelines

1️⃣ What Can and Should be Migrated to Flex

Category FLEX Ready app stacks Why FLEX Ready Not Yet FLEX Ready app stacks Why not yet FLEX Ready
Open-source web appsWordPress, Drupal, Magento, Laravel, Django, Flask, Node.js web appsStandard Linux runtimes, portable app/data tiers, easy VM or app-tier rebuildVery old PHP/Apache apps tied to obsolete OS or local legacy modulesOld runtime, unsupported packages, hidden dependencies
Standard 3-tier business appsWeb + API + DB on supported Linux/WindowsClean separation of app and data tiers, easier rehost or replatformMonolith with app + DB + files + scheduler all on one VMTight coupling, hardcoded paths, embedded dependencies
Open-source databasesMySQL, Percona, PostgreSQL, RedisEasy to move with replication, backup/restore, export/importDB versions too old, unsupported, or bound to obsolete OS/storage stackUpgrade and schema compatibility issues
Standard Windows business appsWindows Server 2019/2022 app servers, IIS apps, .NET-supported appsModern OS, portable workloads, easier rebuild on FLEX VMsWindows 2003/2008 legacy apps, old IIS/.NET dependenciesUnsupported OS, security risk, migration blockers
Linux application tiersUbuntu 20.04/22.04/24.04, RHEL 8/9, Rocky, AlmaLinux, Debian 11/12Supported guest OS, predictable package ecosystemRHEL/CentOS 5/6, Ubuntu 14/16, old Debian, old custom kernelsLegacy kernel/userspace, driver and package issues
API / middleware tiersJava app servers, Tomcat, Spring Boot, Nginx, HAProxy, RabbitMQ, modern middlewareUsually portable if config and connectivity are understoodMiddleware requiring old libraries, old JVM, legacy init scripts, appliance-like packagingRuntime drift and dependency fragility
Containerized workloadsKubernetes apps with portable images, separated PVs, standard registriesStateless layers easy to move, stateful parts manageable with storage planK8s workloads with tangled storage, old CSI bindings, hidden infra dependenciesPV portability and platform coupling issues
File/content platformsShared content repos, NFS-backed app content, object-compatible app dataCan be copied/synced and repointedApps with business logic tightly coupled to local filesystem layoutsHardcoded mounts and path assumptions
ERP/CRM/custom LOB on supported stackSupported OS + supported DB + normal app/data separationCan often be stabilized on FLEX firstOld ERP/CRM on obsolete OS or vendor stack with no clean export pathBetter treated as replacement/replatform project
Analytics / reporting appsModern BI/reporting apps using supported DBs and standard app hostsOften portable if data sources are reachableOld report servers with brittle dependencies and low business valueUsually better to retire or archive
Batch / worker tiersETL jobs, schedulers, queue workers on supported OSEasy to relocate if dependencies are documentedCron-heavy legacy boxes with undocumented local scripts and old runtimesHidden operational logic and local-state risk
Customer-built appsModern custom apps using standard stacks and supported OSBest candidates for phased migrationDeeply customized legacy monolithsNeed refactor/replatform, not simple move
Appliance-like stacksFew, unless virtual appliance is vendor-supported on KVM/FLEXPossible only with explicit supportXen-dependent virtual appliances, proprietary clusters, special kernel appliancesHypervisor dependency or vendor lock-in
Mainframe / proprietary coreDownstream integration to FLEX data onlyFLEX can host replicas, feeds, analyticsMainframe DBs, RAC appliances, proprietary hardware platformsRetain in place, integrate rather than move
