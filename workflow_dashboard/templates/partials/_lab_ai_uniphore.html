🧠 Enterprise AI on a Governed Platform

The city has a nervous system. Now it gets a brain — and rules about what the brain may know.
Boot Camp built the city, Advanced made it safe to operate, and the Kafka lab gave it a nervous system. This lab puts enterprise AI on top of that platform: GPU capacity on FLEX, a model-serving layer, inference driven by real events rather than batch jobs, a retrieval layer over the customer's own records, and the governance that makes it defensible in a regulated account.
Why this lab sits after Kafka, not before it

An AI service that can only be called by an API sees a snapshot. An AI service subscribed to an event stream sees causality — what happened, in what order, and what changed — and can act on it as it happens. Every mission here assumes the event backbone from the Kafka lab already exists. If it does not, build that first; this lab will not work standing alone.

The honest version Most "AI platform" failures are not model failures. They are missing data plumbing, absent governance, and no way to measure whether the thing helped. Missions 4, 7 and 8 exist because those are what actually sink enterprise AI projects.
What you will build
  • A dedicated GPU/AI worker pool on FLEX
  • A model-serving deployment with health and autoscaling
  • An inference request/response topic pair on Kafka
  • A consumer turning business events into inference calls
  • A retrieval (RAG) layer over customer records
  • A <uniphore-connector> integration point
  • PII redaction before anything leaves the cluster
  • Kyverno policy blocking ungoverned AI workloads
  • Token, latency and cost dashboards
  • A model-quality feedback loop on its own topic

2GPU and AI Worker Pools 40 minopencenteropentofu A dedicated district for expensive machines, fenced so nothing else squats on them.
The metaphor GPU nodes are the most expensive buildings in the city. They get their own district, with a gate that only AI workloads can pass — otherwise a batch job schedules onto a GPU node and you pay premium rates for a cron script.
Task 2.1 — Add the pool to the blueprint

Module 8 of the Advanced lab covers this pattern. Add under additional_server_pools via opencenter cluster edit:

additional_server_pools:
  - name: ai-gpu-pool
    count: 2
    flavor: "<gpu-flavor-from-task-1.2>"
    labels:
      workload-class: ai-inference
      accelerator: gpu
    taints:
      - key: workload-class
        value: ai-inference
        effect: NoSchedule
Task 2.2 — Validate, render, deploy
opencenter cluster validate "$LAB_CLUSTER" --validation online
opencenter cluster generate "$LAB_CLUSTER" --render-only --force

git -C "$GITOPS_DIR" add . && git -C "$GITOPS_DIR" commit -m "Add AI GPU worker pool"
git -C "$GITOPS_DIR" push

opencenter cluster deploy "$LAB_CLUSTER" --from-step opentofu-apply
Task 2.3 — Confirm the district exists and is fenced
kubectl get nodes -l workload-class=ai-inference
kubectl describe node -l workload-class=ai-inference | grep -A3 Taints

# The device plugin must expose the GPUs as a schedulable resource
kubectl get nodes -o custom-columns='NAME:.metadata.name,GPU:.status.allocatable.nvidia\.com/gpu'
Nodes are not enough A GPU node with no device plugin reports zero allocatable GPUs and your pods stay Pending forever with no obvious reason. If the column above is empty, the GPU operator or device plugin is missing — confirm which your OpenCenter release installs.
Mission complete when
  • GPU nodes have joined and carry the label and taint.
  • nvidia.com/gpu is allocatable and non-zero.
  • A test pod without the toleration is refused by the district.
3The Model Serving Layer 45 minkubectlflux Somewhere to send a question and reliably get an answer.
The metaphor The brain needs a front desk: one address, a queue, a health check, and the ability to hire more staff when the queue grows.
Task 3.1 — Namespace and model storage
kubectl create namespace "$AI_NAMESPACE" --dry-run=client -o yaml | kubectl apply -f -

cat > "$GITOPS_DIR/ai-model-storage.yaml" <<EOF
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: model-weights
  namespace: ${AI_NAMESPACE}
spec:
  accessModes: [ReadWriteOnce]
  resources:
    requests:
      storage: 200Gi
EOF
Task 3.2 — Deploy the serving workload onto the AI district
spec:
  template:
    spec:
      nodeSelector:
        workload-class: ai-inference
      tolerations:
        - key: workload-class
          value: ai-inference
          effect: NoSchedule
      containers:
        - name: model-server
          image: <your-model-serving-image>
          resources:
            limits:
              nvidia.com/gpu: 1
          readinessProbe:
            httpGet: { path: /health, port: 8080 }
            initialDelaySeconds: 60
          volumeMounts:
            - name: weights
              mountPath: /models
No GPU? The lab still works Drop the nvidia.com/gpu limit, the nodeSelector and the toleration, and use a small CPU model. Every later mission — events, retrieval, governance, cost — is unchanged. Only latency differs.
Task 3.3 — Prove the front desk answers
kubectl -n "$AI_NAMESPACE" rollout status deploy/"$AI_MODEL_NAME"
kubectl -n "$AI_NAMESPACE" port-forward svc/"$AI_MODEL_NAME" 8080:8080 &

curl -s localhost:8080/health
curl -s -X POST localhost:8080/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{"prompt":"Summarise: the migration completed with two warnings.","max_tokens":64}'
The readiness probe is the whole mission Model containers take minutes to load weights. Without a correct initialDelaySeconds Kubernetes kills the pod mid-load and restarts it forever. If your model server crash-loops, this is why — before you blame the image.
Mission complete when
  • The deployment is Ready on a GPU (or documented CPU) node.
  • /health returns healthy and an inference call returns a real completion.
  • Weights load from the PVC, not baked into the image.

4Event-Driven Inference on Kafka 45 minkafkastrimzi The brain stops waiting to be asked and starts reacting to what happens.
The metaphor Until now the brain answers only when someone walks up and asks. Connect it to the railway and it reacts to every parcel passing through the city — and its answers become parcels other services can collect.
Task 4.1 — Create the inference topic pair
for T in "$AI_TOPIC_IN" "$AI_TOPIC_OUT" "$AI_TOPIC_FEEDBACK"; do
cat > "$GITOPS_DIR/kafka-topic-$T.yaml" <<EOF
apiVersion: kafka.strimzi.io/v1beta2
kind: KafkaTopic
metadata:
  name: ${T}
  namespace: ${KAFKA_NAMESPACE}
  labels:
    strimzi.io/cluster: ${KAFKA_CLUSTER}
spec:
  partitions: 6
  replicas: 3
EOF
done

git -C "$GITOPS_DIR" add . && git -C "$GITOPS_DIR" commit -m "Add AI inference topics"
git -C "$GITOPS_DIR" push && flux reconcile source git flux-system
Task 4.2 — The event contract

Agree the shape before writing the consumer. This is the interface between the business and the model, and changing it later breaks every consumer.

{
  "event_id":     "uuid",
  "occurred_at":  "2026-07-31T20:14:00Z",
  "source":       "cutover-service",
  "subject":      "acme-payments",
  "task":         "summarise | classify | extract",
  "payload":      { "...": "already PII-redacted, see Mission 7" },
  "trace_id":     "for joining request to result"
}
Task 4.3 — Run the inference worker

A consumer in group ai-workers reads $AI_TOPIC_IN, calls the model service, and produces to $AI_TOPIC_OUT carrying the same trace_id. Scale it by adding replicas — the consumer group rebalances partitions automatically, exactly as in Kafka lab Mission 5.

kubectl -n "$AI_NAMESPACE" scale deploy/ai-inference-worker --replicas=3

# Lag is your AI backlog. This is the number that matters.
kubectl -n "$KAFKA_NAMESPACE" run kafka-admin -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-consumer-groups.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --describe --group ai-workers
Why this beats a REST call A slow model no longer blocks the business app — requests queue instead of timing out. Bursts are absorbed. The model can be restarted or upgraded with zero lost requests. And you can replay a day of traffic through a new model version to compare it against the old one before switching. None of that is available over synchronous HTTP.
Mission complete when
  • All three topics exist and are Ready.
  • An event on the request topic produces a result on the result topic with a matching trace_id.
  • Scaling the worker changes partition assignment and reduces lag.
  • Killing the model service causes lag to grow — and no events to be lost.
5Uniphore Platform Integration 45 minuniphorekubectl Connect the platform you built to the enterprise AI product the customer bought.
Highest-placeholder mission — confirm everything Every identifier in this mission is written <uniphore-*> because I will not invent a vendor's API surface. Before delivering: get the current integration guide from Uniphore, confirm what the Rackspace partnership entitles the customer to, and replace each placeholder. The shape of the integration below (credentials as Secrets, egress policy, a bridge on the event backbone, health verification) is correct regardless of the product's specifics.
Task 5.1 — Store tenant credentials as a Secret, never in Git plaintext
kubectl -n "$AI_NAMESPACE" create secret generic uniphore-tenant \
  --from-literal=endpoint="$UNIPHORE_ENDPOINT" \
  --from-literal=tenant-id="$UNIPHORE_TENANT" \
  --from-literal=api-key='<uniphore-api-key>' \
  --dry-run=client -o yaml > uniphore-tenant.yaml

# Encrypt before it goes near Git - Advanced lab Module 7
opencenter secrets encrypt --path applications/overlays/"$LAB_CLUSTER"
Never commit this unencrypted A vendor API key in Git history is a credential rotation and an incident report, even in a private repo. SOPS-encrypt it or use a secret store — there is no third acceptable option.
Task 5.2 — Open only the egress the integration needs
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-uniphore-egress
  namespace: <ai-namespace>
spec:
  podSelector:
    matchLabels: { app: uniphore-bridge }
  policyTypes: [Egress]
  egress:
    - to:
        - ipBlock:
            cidr: <uniphore-endpoint-cidr>
      ports:
        - protocol: TCP
          port: 443

Default-deny plus one explicit allow. If the customer is regulated, this policy is the artifact their auditor will ask to see — it proves the AI namespace cannot call anywhere else.

Task 5.3 — The bridge

A deployment that consumes $AI_TOPIC_OUT and forwards to <uniphore-ingest-endpoint>, and/or consumes <uniphore-event-source> and produces onto $AI_TOPIC_IN. Kafka is deliberately in the middle: the vendor platform and your business systems never talk directly, so either side can be replaced without touching the other.

kubectl -n "$AI_NAMESPACE" rollout status deploy/uniphore-bridge
kubectl -n "$AI_NAMESPACE" logs deploy/uniphore-bridge --tail=50

# Verify the allowlist works in BOTH directions
kubectl -n "$AI_NAMESPACE" exec deploy/uniphore-bridge -- \
  curl -s -o /dev/null -w '%{http_code}\n' https://example.com   # expect failure
Mission complete when
  • Credentials exist as an encrypted Secret, absent from Git plaintext.
  • Egress is default-deny with a single documented exception.
  • The bridge is running and a round trip is demonstrated end to end.
  • A call to any non-allowlisted host is refused, with the failure captured.
  • Every <uniphore-*> placeholder has been replaced with a confirmed value.
6Retrieval and the Knowledge Layer 40 minkubectlpostgres Give the brain the customer's own records, so it stops inventing answers.
The metaphor A brilliant employee who has never read the company's files will confidently give wrong answers. Retrieval is handing them the filing cabinet — and requiring them to cite which file they used.
Task 6.1 — Stand up the vector store

You already run postgres-operator from the platform services. A PostgreSQL database with a vector extension avoids adding another stateful system to operate.

kubectl -n "$AI_NAMESPACE" get pods -l application=spilo
kubectl -n "$AI_NAMESPACE" exec -it <postgres-pod> -- \
  psql -c 'CREATE EXTENSION IF NOT EXISTS vector;'
Task 6.2 — Ingest through the event backbone, not a batch script

Documents and record changes arrive as events; an embedding consumer writes vectors. The knowledge layer then stays current automatically instead of being re-indexed nightly and drifting all day.

source record changes
      ↓
Kafka topic: knowledge-updates
      ↓
embedding consumer  →  vector store
      ↓
retrieval API  →  model prompt (with citations)
Task 6.3 — Require citations
The rule that makes RAG defensible An answer with no citation is not an answer, it is a guess with good grammar. Configure the retrieval layer to return source ids alongside the text, and have the serving layer refuse to answer when retrieval returns nothing. "I don't have that information" is a correct, valuable output — a confident fabrication is a liability in a regulated account.
Mission complete when
  • The vector store is running with a working extension.
  • A record change event results in an updated embedding, with no manual step.
  • A query returns an answer with citations to source records.
  • A query with no relevant records returns a refusal, not an invention.
Part 3 · Make it defensible Missions 7–9🔐 Governance, measurement, exit
7Governance, PII and Guardrails 45 minkyvernokeycloak The mission that decides whether this ever reaches production.
The metaphor The brain is capable. Now the city decides what it is permitted to know, who may ask it, and what it must never repeat.
Task 7.1 — Redact before the data leaves its home namespace

Redaction belongs at the producer, not the model. Once an unredacted value is on a topic it is retained, replicated and replayable — a retention policy problem, not a prompt problem.

Business system
      ↓  redact here  ← account numbers, names, card data, health identifiers
Kafka: ai-inference-requests
      ↓
model  — never sees the original values
Task 7.2 — Block ungoverned AI workloads with policy
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: require-ai-governance
spec:
  validationFailureAction: Enforce
  rules:
    - name: require-data-classification
      match:
        any:
          - resources:
              kinds: [Deployment]
              namespaces: [<ai-namespace>]
      validate:
        message: "AI workloads must declare data-classification and model-owner labels."
        pattern:
          metadata:
            labels:
              data-classification: "?*"
              model-owner: "?*"

Now an undocumented model cannot be deployed at all. That is a far stronger control than a policy document nobody reads.

Task 7.3 — Authenticate and authorise callers
kubectl get pods -n keycloak
# Who may call the model? Which team owns which topic?

Task 7.4 — The challenge
Prove all five, with evidence
  • A PII value entering the business system never appears on any Kafka topic.
  • A Deployment without governance labels is rejected — capture the Kyverno message.
  • An unauthenticated caller cannot reach the model service.

8Observability, Quality and Cost 35 minprometheusgrafana Answer the only two questions leadership will actually ask.
The two questions "Is it working?" and "What is it costing us?" A platform that cannot answer both gets switched off at the next budget review, however good the technology is.
Task 8.1 — The metrics that matter
SignalWhy it earns its dashboard space
Consumer lag on $AI_TOPIC_INThe AI backlog. Rising lag = users waiting. Alert on this.
Inference latency p50/p95/p99p99 is what users complain about; averages hide it
Tokens in / out per requestThe unit of cost. No tokens metric, no cost model.
GPU utilisationLow utilisation on premium nodes is money burning quietly
Refusal / no-citation rateRising refusals mean the knowledge layer is stale
Feedback topic volumeHumans disagreeing with the model — your quality signal
Task 8.2 — Close the quality loop

Human corrections publish to $AI_TOPIC_FEEDBACK. That topic is the training set for the next iteration and the evidence that the system is improving — which is what renews the budget.

kubectl -n "$KAFKA_NAMESPACE" run kafka-admin -ti \
  --image="$KAFKA_CLIENT_IMAGE" --rm=true --restart=Never -- \
  bin/kafka-console-consumer.sh \
    --bootstrap-server "$KAFKA_CLUSTER-kafka-bootstrap:9092" \
    --topic "$AI_TOPIC_FEEDBACK" --from-beginning --timeout-ms 10000
Task 8.3 — Cost per outcome, not cost per node
The number that wins the argument "GPU nodes cost $X/month" invites a cut. "Each handled ticket costs $0.04 in inference against $6.00 of agent time" ends the conversation. Build the second number: total inference cost divided by business events successfully handled. You need the tokens metric from 8.1 to do it.
Mission complete when
  • A dashboard shows lag, latency percentiles, tokens and GPU utilisation.
  • An alert fires on sustained lag.
  • The feedback topic is receiving real human corrections.
  • You can state cost per business outcome, not just cost per node.
