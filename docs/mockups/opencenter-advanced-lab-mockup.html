The story

You are the platform team for Aurora Labs, a regulated digital-services company. You must launch a secure Kubernetes platform on OpenStack, grow it into a multi-cluster fleet, survive failures, perform an upgrade, and migrate an application without losing data. Every lab earns XP and ends with an evidence checkpoint rather than "it looks okay."

Learning outcomes

  • Design and create a v2 OpenCenter cluster configuration using guided or manual workflows.
  • Validate provider, network, GitOps, service, and secret dependencies before deployment.
  • Generate and operate the GitOps repository, including reconciliation and rollback.
  • Select and configure platform services, CNI, load balancing, DNS, TLS, and policy.
  • Encrypt, rotate, and recover secrets with SOPS and Age.
  • Add specialized worker pools and control workload placement with labels and taints.
  • Back up and restore cluster state and applications.
  • Upgrade Kubernetes using prechecks, controlled rollout, verification, and rollback gates.
  • Manage dev, staging, and production clusters with shared organization defaults.
  • Plan and execute provider or region migration with a tested cutover and rollback plan.
  • Diagnose failures from configuration through cloud infrastructure, Kubernetes, Flux, and services.

Lab conventions

  • Replace values inside <angle-brackets> before execution.
  • SAFE — read-only, local, validation, or dry-run operations.
  • CHANGE — modifies Git, cluster state, or infrastructure.
  • DESTRUCTIVE — requires an explicit instructor checkpoint.
  • Use an application credential, never a personal username/password, for OpenStack automation.
  • Confirm supported Kubernetes, CNI, and service versions in your installed OpenCenter release.
  • Use opencenter <command> --help when the lab environment differs from the reference build.

1Guided Cluster Design 60 min100 XPConfig Navigator Create the v2 source of truth.

Mission — Create a production-shaped OpenStack cluster configuration using guided discovery, then inspect the resulting v2 structure.

Why this workflow Guided mode discovers images, flavors, networks, subnets, external networks and availability zones — and keeps the duplicated OpenStack network fields synchronized, which manual editing does not.
Step 1 — Guided configuration CHANGE: local files
opencenter cluster configure "$OC_CLUSTER" \
  --guided \
  --org "$OC_ORG" \
  --type openstack

# re-run to fill unresolved placeholders
opencenter cluster configure "$OC_REF" --guided

During the prompts, select:

  • Application credential authentication.
  • An approved Ubuntu image.
  • Three control-plane nodes and two workers — or one plus two for a low-cost sandbox.
  • One CNI only.
  • A Git remote and branch.
  • DNS and object-storage values only for services you plan to enable.
Step 2 — Describe resolved paths SAFE
opencenter cluster describe "$OC_REF" | tee ~/opencenter-training-evidence/01-config/describe.txt

Locate the cluster config path, GitOps working directory, cluster-owned kubeconfig, SSH key location and SOPS Age key location.

Step 3 — Inspect, do not expose

  meta:
    env: production
    region: <region>
  cluster:
    cluster_fqdn: <cluster-fqdn>
    admin_email: <platform-email>
  gitops:
    repository:
      url: <git-url>
      branch: main
  infrastructure:
    cloud:
      openstack:
        auth_url: <keystone-v3-url>
        project_id: <project-id>
        application_credential_id: <app-cred-id>
        application_credential_secret: <protected-secret>
        image_id: <image-id>
        network_id: <network-id>
        subnet_id: <subnet-id>
        router_external_network_id: <external-network-id>
Never copy secrets Confirm these sections exist without pasting values into chat, tickets, or screenshots.
Step 4 — Architecture decision record

Create 01-config/ADR-001-cluster-shape.md covering availability target, node counts and flavors, CNI choice, load-balancer choice, storage class, expected failure domains, and the lab-versus-production cost trade-off.

Evidence checkpoint
  • v2 configuration exists under the organization-aware directory.
  • Git repository URL is not a placeholder.
  • Exactly one CNI is enabled.
  • Node, pod, and service CIDRs do not overlap.
  • ADR explains every major choice.
Challenge card — "Manual lane" Initialize a second disposable config with cluster init --full-schema, then identify five fields guided mode would have populated more safely.

Mission — Use layered validation so failures occur in seconds, not halfway through infrastructure provisioning.

The validation ladder
GateCommandWhat it proves
Workstationcluster doctorRequired local tools and basic provider hints
OfflinevalidateSchema, required fields, dependencies, CIDRs, Git/SOPS shape
Onlinevalidate --validation onlineProvider discovery/connectivity and Git remote checks
Rendergenerate --dry-runTemplates resolve without writing

Step 1 — Doctor and offline validation SAFE
opencenter cluster doctor "$OC_REF"
opencenter cluster validate "$OC_REF" --verbose \
  | tee ~/opencenter-training-evidence/02-validation/offline.txt
Step 2 — Online validation SAFE · external calls
opencenter cluster validate "$OC_REF" --validation online --output json \
  | tee ~/opencenter-training-evidence/02-validation/online.json
Step 3 — Debug artifact SAFE · may contain secrets
mkdir -p ~/opencenter-training-evidence/02-validation/debug
opencenter cluster validate "$OC_REF" \
  --generate-debug-config \
  --output-dir ~/opencenter-training-evidence/02-validation/debug
chmod -R go-rwx ~/opencenter-training-evidence/02-validation/debug
Do not commit this directory The debug config contains fully resolved values, including sensitive ones.
Step 4 — Break/fix circuit

The instructor assigns one fault:

  • Invalid CIDR prefix.
  • Overlapping pod and service networks.
  • Two CNIs enabled.
  • Missing application credential ID.
  • VRRP enabled without vrrp_ip.
  • Git origin mismatch.
  • Missing SOPS key.

Run validation, capture the exact field path, repair, and rerun until green.

Step 5 — Preview SAFE
opencenter cluster generate "$OC_REF" --dry-run
opencenter cluster deploy   "$OC_REF" --dry-run
Evidence checkpoint Submit a two-column record: failure observed and proof of repair. A passing command without the failure evidence earns only half credit.
Challenge card — "CI gate" Write a shell gate that fails a pipeline when online validation returns a non-zero exit code, and preserves the JSON as a build artifact.
Reset Return the configuration to a passing state and remove any deliberate fault.
Level 2 · Delivery Engine GitOps, services, networking 🏅 GitOps Pilot
3GitOps Engine Room 70 min125 XPGitOps Pilot Generate, publish, reconcile, and roll back.

Mission — Generate the repository, understand every major directory, publish the initial commit, and prove that Git — not an operator laptop — is the desired-state source.

Step 1 — Generate repository CHANGE: local Git
opencenter cluster generate "$OC_REF"

GITOPS_DIR=$(opencenter cluster describe "$OC_REF" 2>/dev/null | awk '/git_dir:/ {print $2}')
find "$GITOPS_DIR" -maxdepth 4 -type d | sort | tee ~/opencenter-training-evidence/03-gitops/tree.txt
git -C "$GITOPS_DIR" log --oneline -3
Step 2 — Map the repository
applications/overlays/<cluster>/
  flux-system/       Flux bootstrap and sources
  services/          Platform-service desired state
  managed-services/  Customer/application workloads
infrastructure/clusters/<cluster>/
  provider.tf        OpenTofu provider/backend
  main.tf            Cloud resources
  inventory/         Cluster provisioning inputs
  kubeconfig.yaml    Cluster-owned kubeconfig after deployment
Step 3 — Publish initial state CHANGE: remote Git
git -C "$GITOPS_DIR" remote add origin "$OC_GIT_URL" 2>/dev/null || \
  git -C "$GITOPS_DIR" remote set-url origin "$OC_GIT_URL"
git -C "$GITOPS_DIR" branch -M main
git -C "$GITOPS_DIR" push -u origin main
git -C "$GITOPS_DIR" remote -v
Step 4 — Deploy and observe CHANGE: cloud infrastructure
opencenter cluster deploy "$OC_REF" --confirm-commit
#Step ID
1openstack-preflight
2opentofu-init
3opentofu-apply
4openstack-normalize-kubeconfig
5openstack-install-network-plugin
Completion is API reachability Deployment returns when the Kubernetes API is reachable. Flux and platform services may still be reconciling — that is expected, not a failure.
Step 5 — Prove reconciliation
eval "$(opencenter cluster use "$OC_REF" --export-only)"
kubectl cluster-info
kubectl get nodes -o wide
kubectl get pods -n flux-system
flux get sources git -A
flux get kustomizations -A
Step 6 — Controlled rollback
git -C "$GITOPS_DIR" revert <commit-sha>
git -C "$GITOPS_DIR" push
flux reconcile source git flux-system -n flux-system
Evidence checkpoint
  • Git origin equals the configured repository URL.
  • All nodes are Ready.
  • Flux source and kustomizations converge.
  • A Git revert restores the previous desired state.
Challenge card — "Interrupted deployment" The instructor stops a run after OpenTofu initialization. Resume with --from-step, explain saved state and locks, and avoid a full restart.
Reset Leave the repository clean and Flux reconciled. Do not destroy infrastructure.

  • The change is visible in Git history and in the cluster.

Mission — Create a network design that is routable, non-overlapping, observable, and least-privilege.

Step 1 — Address plan

Node subnet10.2.128.0/22Pod, service, corporate/VPN routes
Pod subnet10.42.0.0/16Node, service, peer clusters
Service subnet10.43.0.0/16Node, pod, peer clusters

Step 2 — Select exactly one CNI
opencenter:
  cluster:
    kubernetes:
      network_plugin:
        calico:   { enabled: true, install_method: helm }
        cilium:   { enabled: false }
        kube-ovn: { enabled: false }
  • Calico — familiar network policy, broad operational experience.
  • Cilium — eBPF visibility and advanced networking features.
  • Kube-OVN — OVN integration and virtual-network features.

opencenter:
  infrastructure:
    networking:
      use_octavia: true
      loadbalancer_provider: octavia
      vrrp_enabled: false

Step 4 — Lock down the Kubernetes API
opencenter:
  infrastructure:
    cloud:
      openstack:
        networking:
          k8s_api_port_acl:
            - "<office-or-vpn-cidr>"
Step 5 — Validate and render
opencenter cluster validate "$OC_REF" --validation online
opencenter cluster generate "$OC_REF" --render-only --force
git -C "$GITOPS_DIR" diff
Step 6 — Apply a default-deny policy CHANGE: namespace
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny-all
  namespace: network-lab
spec:
  podSelector: {}
  policyTypes: [Ingress, Egress]

Add controlled allow rules for DNS and the test application. Prove an unauthorized pod cannot connect and an authorized pod can.

Step 7 — Diagnose from outside in

kubectl get gateway,httproute -A
kubectl get svc,endpoints -A

Evidence checkpoint

  • One CNI and one load-balancing strategy are enabled.
  • API allowlist excludes 0.0.0.0/0 for production.
  • Default-deny and explicit-allow behavior are demonstrated.
Challenge card — "Pending external IP" A LoadBalancer service remains pending. Trace provider, controller, quota, subnet, security-group, and service events — in that order.

6Secrets Vault 65 min125 XPVault Keeper Encrypt, rotate, and recover without leaking plaintext.

Mission — Operate the full secret lifecycle: generate, encrypt, decrypt locally, rotate, and recover.

Step 1 — Locate and protect keys SAFE
opencenter cluster describe "$OC_REF"
find ~/.config/opencenter/clusters/"$OC_ORG"/secrets -maxdepth 3 -type f -ls
chmod 600 ~/.config/opencenter/clusters/"$OC_ORG"/secrets/age/* 2>/dev/null || true
Step 2 — Create a lab secret
apiVersion: v1
kind: Secret
metadata:
  name: payment-api
  namespace: secrets-lab
type: Opaque
stringData:
  API_TOKEN: replace-me
Step 3 — Encrypt before commit CHANGE: Git file
opencenter secrets encrypt --path "$GITOPS_DIR/applications/overlays/$OC_CLUSTER"
grep -R "ENC\[AES256_GCM" "$GITOPS_DIR/applications/overlays/$OC_CLUSTER" | head

# prove the plaintext is gone
! grep -R "replace-me" "$GITOPS_DIR/applications/overlays/$OC_CLUSTER"
Step 4 — Commit and reconcile
git -C "$GITOPS_DIR" add .
git -C "$GITOPS_DIR" commit -m "feat(security): add encrypted payment API secret"
git -C "$GITOPS_DIR" push
flux get kustomizations -A
Step 5 — Rotate the cluster key
opencenter secrets keys rotate --cluster "$OC_REF" --type age
opencenter secrets keys check  --org "$OC_ORG"
Step 6 — Recovery drill

The instructor temporarily removes the local key. Learners must:

  1. Identify the decryption failure.
  2. Restore the protected backup key.
  3. Repair file permissions.
  4. Reconcile Flux.
  5. Prove the secret exists in-cluster without printing its value.
kubectl get secret payment-api -n secrets-lab
kubectl describe secret payment-api -n secrets-lab
Evidence checkpoint
  • No plaintext secret exists in Git.
  • Key permissions are restrictive.
  • Rotation is recorded and files are re-encrypted.
  • Recovery restores reconciliation.
Challenge card — "Shared versus cluster-specific" Design .sops.yaml rules for organization-shared secrets and separate dev/staging/prod keys. Explain the blast radius of each choice.
Reset Delete the lab namespace only after evidence is collected. Preserve rotated keys securely.
7Elastic Capacity 70 min125 XPCapacity Engineer Add specialized worker pools and control placement.

Mission — Add high-memory, GPU, or tenant-dedicated capacity while preventing ordinary workloads from landing there.

Step 1 — Design pools
opencenter:
  cluster:
    additional_server_pools:
      - name: highmem
        count: 2
        flavor: <high-memory-flavor>
        labels: { pool: highmem, workload-type: data-processing }
        taints:
          - { key: workload-type, value: data-processing, effect: NoSchedule }
        volume_size: 100
        volume_type: <volume-type>
      - name: gpu
        count: 1
        flavor: <gpu-flavor>
        labels: { pool: gpu, accelerator: nvidia }
        taints:
          - { key: nvidia.com/gpu, value: "true", effect: NoSchedule }
Step 2 — Validate the capacity plan
openstack quota show
opencenter cluster validate "$OC_REF" --validation online

Calculate total instances, vCPU, RAM, volume and GPU demand, and compare against provider quota before applying.

Step 3 — Render and review infrastructure change
opencenter cluster generate "$OC_REF" --render-only --force
cd "$GITOPS_DIR/infrastructure/clusters/$OC_CLUSTER"
opentofu init
opentofu plan | tee ~/opencenter-training-evidence/07-pools/tofu-plan.txt
Apply only after instructor approval Use the supported provider workflow — the plan output is the artifact to review first.
Step 4 — Verify labels and taints
kubectl get nodes -L pool,workload-type,accelerator
kubectl get nodes -o json | jq '.items[] | {name:.metadata.name,taints:.spec.taints}'
Step 5 — Placement test
spec:
  nodeSelector:
    pool: highmem
  tolerations:
    - key: workload-type
      operator: Equal
      value: data-processing
      effect: NoSchedule
  containers:
    - name: demo
      image: nginx:stable
      resources:
        requests: { cpu: "500m", memory: "512Mi" }
Evidence checkpoint
  • Provider quota supports the plan.
  • Infrastructure plan shows only intended additions.
  • Specialized nodes are Ready with correct labels/taints.
  • Test pod lands on the intended pool.
  • A pod without toleration remains unscheduled.
Challenge card — "Noisy neighbor" Design a dedicated tenant pool with taints, namespace quota, limit range, and policy. Explain which control handles placement versus consumption.
Reset Scale or remove expensive GPU capacity after the lab, per instructor policy.

Level 4 · Resilience & Evolution Backup/restore, upgrade, multi-cluster 🏅 Reliability Guardian
9Resilience Lab 90 min175 XPReliability Guardian Back up and restore cluster state and applications.

Mission — Prove recovery, not merely backup creation.

Recovery model
LayerTypical mechanismProtects
GitRemote Git + historyDesired state and audit trail
etcdScheduled snapshotsKubernetes API state
VeleroObject storage + volume snapshotsNamespaces, resources, application data
ProviderVolume/image snapshotsInfrastructure or data volumes
Step 1 — Define RPO and RTO

Record maximum acceptable data loss, maximum acceptable recovery time, backup frequency, retention, and restore target (same cluster and alternate cluster).

Step 2 — Verify backup components
kubectl get pods -n velero
velero backup-location get
velero snapshot-location get
kubectl get cronjobs -A | grep -E 'backup|etcd'
Step 3 — Create test data and backup
kubectl create namespace recovery-lab
kubectl create configmap recovery-marker \
  --from-literal=value="before-failure" -n recovery-lab

velero backup create recovery-lab-001 --include-namespaces recovery-lab --wait
velero backup describe recovery-lab-001 --details
Step 4 — Failure injection DESTRUCTIVE: namespace only
kubectl delete namespace recovery-lab
Step 5 — Restore and verify
velero restore create --from-backup recovery-lab-001 --wait
kubectl get namespace recovery-lab
kubectl get configmap recovery-marker -n recovery-lab -o yaml
Step 6 — Alternate-cluster rehearsal

Restore into a designated recovery cluster, or simulate with a second namespace. Identify storage-class mappings, DNS changes, external secrets and provider-specific resources that require translation.

Step 7 — Measure recovery

Record detection time, decision time, restore duration, validation duration, total RTO, and data loss versus RPO.

Evidence checkpoint
  • Backup completed and stored in an accessible location.
  • Namespace deletion is recovered.
  • Marker data is intact.
  • Measured RPO/RTO meets or misses the target explicitly.
  • Alternate-cluster gaps are documented.
Challenge card — "Backup succeeds, restore fails" The backup exists but a PVC remains Pending on the target. Diagnose storage class, CSI driver, snapshot location, access mode, and zone constraints.
Reset Keep one known-good backup for the migration labs. Remove temporary restores after instructor approval.
10Upgrade Flight Simulator 80 min150 XPUpgrade Commander Upgrade with gates, canaries, and rollback criteria.

Mission — Plan and rehearse a Kubernetes upgrade without treating a version change as a single command.

Step 1 — Baseline
kubectl version
kubectl get nodes -o wide
kubectl get pods -A
flux get kustomizations -A
kubectl get --raw='/readyz?verbose'
Step 2 — Compatibility matrix

Current and target Kubernetes versions · CNI · CSI/CCM · Flux controllers · cert-manager, Gateway API, Keycloak, observability, Velero · application APIs and deprecated resources.

Step 3 — Upgrade gates
Do not proceed unless
  • Backup/restore was tested.
  • Cluster is healthy.
  • Target version is supported by OpenCenter and provider tooling.
  • Disruption budgets permit node drains.
  • Capacity can absorb one unavailable node.
  • Rollback trigger and decision owner are named.
Step 4 — Change configuration and render
opencenter cluster set "$OC_REF" opencenter.cluster.kubernetes.version=<target-version>
opencenter cluster validate "$OC_REF" --validation online
opencenter cluster generate "$OC_REF" --render-only --force
git -C "$GITOPS_DIR" diff
Step 5 — Controlled rollout

Migration choices
StrategyDowntimeComplexityWhen to use
Dual run / traffic shiftNear zeroHighCritical services with compatible data replication

Phase 1 — Discover
  • Namespaces, deployments, stateful sets, jobs, CRDs.
  • PVCs, storage classes, snapshots, object storage.
  • DNS, certificates, gateways, load balancers, firewall rules.
  • ConfigMaps, encrypted secrets, external secret systems.

Phase 3 — Rehearse restore

  --wait
Phase 4 — Cutover plan

The runbook must name: freeze time and owner, final backup/replication checkpoint, DNS TTL reduction timing, traffic-switch mechanism, validation probes, rollback trigger, maximum decision time, and communication cadence.

Phase 5 — Execute CHANGE
  1. Freeze writes.
  2. Create final backup/snapshot.
  3. Restore or complete replication.
  4. Run target smoke tests.
  5. Switch DNS/load balancer/route.
  6. Unfreeze writes.
  7. Watch error rate, latency, data consistency, background jobs.
Phase 6 — Rollback test
A rollback plan that ignores data divergence is incomplete Before production cutover, prove you can route back and reconcile any data written after the switch.
Evidence checkpoint
  • Dependency map and migration wave exist.
  • Rehearsal restore succeeds.
  • Cutover runbook names owners and timings.

  • Rollback includes data-consistency handling.
